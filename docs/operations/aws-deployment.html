Why this architecture

Each choice below comes from a requirement the template already has: several independently released services, cookie sessions for the browser, background side effects, and no single availability zone as a point of failure. The last column points to the decision record in docs/adr/ that explains it in full.

DecisionWhyTrade-off acceptedADR
Containers on EKS, deployed with Helm Every service ships as an image with its own Helm release, so teams release independently. Kubernetes gives autoscaling, disruption budgets, NetworkPolicies and rolling updates out of the box, and the same charts run on GKE or AKS. A cluster to operate and a fixed control-plane fee per cluster. Smaller teams may prefer ECS (see below). 0013 0016
Three subnet tiers; only the load balancer and NAT are public Pods, Redis and the database have no public address. RDS and Redis security groups accept connections only from the cluster, so a leaked credential is useless from the internet. Outbound calls need NAT gateways, which cost per hour and per GB. 0013
One origin: / to the web app, /v1 and /v2 to the API Session cookies stay first-party and SameSite, the CSRF double-submit works, and there is no CORS configuration to get wrong. The web app and the API share one hostname and one ingress. 0008 0014
CloudFront and AWS WAF in front TLS ends close to users, static SPA assets are cached at the edge, and managed WAF rules and rate rules drop bad traffic before it reaches the cluster. One more layer to configure, owned by the platform stack rather than this repository. 0013
NLB + ingress-nginx rather than an ALB Ingress The chart's Ingress uses the nginx class and its annotations (body-size limit, forced HTTPS), which behave the same on every cloud and locally. You run and upgrade the ingress controller yourself. 0013
RDS PostgreSQL 16, Multi-AZ, 35-day point-in-time restore A synchronous standby in a second zone takes over automatically, and backups cover operator mistakes as well as hardware loss. TLS is enforced and slow queries are logged. The standby doubles the instance cost and serves no reads. 0012
One database server, one schema per service Each service owns its tables and roles and references other data by ID only, so services stay independent without paying for an instance each. Services share the server's capacity and maintenance window. Give a service its own instance when it needs isolation. 0016
ElastiCache Redis Rate-limit counters must be shared by every API replica, and the ARQ worker needs a queue. Production runs two nodes with failover; TLS and an auth token are always on. One more managed service; Redis is required in every deployed environment. 0006 0010
Separate worker with a transactional outbox E-mail and other side effects never slow a request, and an event exists only if its business change committed. Several workers can run safely. Side effects arrive a few seconds after the response instead of inside it. 0010
Private S3 bucket, accessed through an IAM role (IRSA) Pods stay stateless, so any replica can serve any file, and there are no access keys to leak. Versioning and KMS protect against deletion and disclosure. The IAM role and its trust policy must be created with the cluster. 0005
Secrets Manager synced by External Secrets No secret is stored in Git or Helm values, secrets rotate in one place, and the services refuse to start with default secrets outside development. An operator to run, and a short delay before a rotated value reaches the pods. 0007
Migrations as a Helm pre-upgrade Job Exactly one runner applies them before any new pod starts. If a migration fails, the rollout stops and the old version keeps serving. Migrations must be backward compatible (expand, then contract), because old pods keep running during the rollout. 0012 0013
3 or more API pods spread across zones, at least 2 always up Losing a node or a whole zone, or draining nodes for an upgrade, never takes the API down. The autoscaler adds pods up to 12 under load. Three pods run even when traffic is low. 0013
Build once, promote the same image digests Production runs exactly the bytes that passed staging, and a rollback is a redeploy of the previous digest. Environment differences must live in configuration, never in the image. 0013
Domain services verify tokens offline data-acquisition checks identity's access tokens itself, so no request depends on identity being reachable. The HS256 signing key is shared; move to asymmetric keys and JWKS when more services trust identity. 0016

What happens when one availability zone fails

ComponentBehaviour in production
Load balancerKeeps serving from the remaining zones.
identity API and webPods in the other zones keep serving (at least 2 API pods are guaranteed), and replacements are scheduled there.
RDS PostgreSQLFails over to the standby automatically, typically within one to two minutes. Requests in that window fail and clients retry.
ElastiCache RedisThe replica is promoted; rate limits and queued jobs continue.
NAT gatewayEach zone has its own, so outbound e-mail and error reporting continue. Staging shares one NAT and loses egress if that zone fails.
S3 and Secrets ManagerRegional services, unaffected by the loss of one zone.

First deployment, in order

  1. In your platform stack, create the EKS cluster, the Route 53 zone, CloudFront and the WAF.
  2. From deploy/terraform/aws, run terraform apply -var-file=envs/production.tfvars, passing the cluster's node security group in app_security_group_ids.
  3. Install the cluster add-ons: AWS Load Balancer Controller, ingress-nginx, cert-manager with a letsencrypt issuer, External Secrets Operator and, optionally, kube-prometheus-stack.
  4. Run deploy/db/roles.sql and roles-data-acquisition.sql against RDS, then replace app_admin in Secrets Manager with those least-privilege roles.
  5. Create the ExternalSecrets app-secrets and data-acquisition-secrets. The data-acquisition JWT_SECRET_KEY must be identity's signing key, because both verify the same HS256 tokens.
  6. Create the IAM role for the API's service account with access to the uploads bucket and set it in serviceAccount.annotations.
  7. Build and push the three images, and replace the ghcr.io/your-org/your-repo placeholders in the values files.
  8. Run helm upgrade --install for deploy/helm/app with values-production.yaml, ingress.host and config.S3_BUCKET (the chart refuses to install without it), then for deploy/helm/domain-service.
  9. Point CloudFront's origin at the load balancer and the Route 53 record at CloudFront.

Close before go-live

  • Add a CI workflow: the release flow above assumes one, and the repository has none yet.
  • data-acquisition has no Ingress route. Add one (for example /acquisition) if browsers or other clients must reach it.
  • S3 traffic currently leaves through the NAT gateways. A VPC gateway endpoint for S3 keeps it inside AWS and lowers NAT cost.
  • Rotate the generated secrets in Secrets Manager and replace the app_admin database user, as the Terraform comments ask.
