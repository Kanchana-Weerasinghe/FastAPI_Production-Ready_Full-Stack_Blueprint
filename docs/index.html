What problem does this template solve?

A new application should not have to rediscover safe defaults, transaction handling, module boundaries, API error conventions, testing patterns, and deployment mechanics before its team can build product features.

The template provides a working application skeleton with those cross-cutting concerns already represented. It aims to make the common path explicit: add a business domain, keep its rules close together, expose a stable API, test it against realistic infrastructure, and promote the same built artifact through environments.

Intended use: a production-minded baseline for teams building a larger application as a modular monolith. It is not a certification, a turnkey hosted platform, or a claim that one deployment configuration fits every workload.

It helps prevent

  • Business logic scattered across global route/service/repository folders.
  • Services committing partial state or raising HTTP errors from domain code.
  • Unbounded list queries and unstable client error contracts.
  • Fragile retries for writes and lost side effects after database commits.
  • Tests accidentally resetting a developer or shared database.
  • Deployments that silently rely on placeholder domains or infrastructure.

It does not decide for every product

  • Tenant isolation strategy, regulatory obligations, or data residency.
  • Identity-provider selection, product-specific authorization policy, or SLOs.
  • Capacity, cache invalidation, read replicas, and business-specific workflows.
  • Managed Kubernetes, DNS, WAF, certificate, or monitoring ownership.
  • Whether a future domain should become a separate service.

Design principles and patterns

This section describes design principles demonstrated by the implementation: DDD-inspired domain modeling, SOLID, separation of concerns, dependency inversion, and patterns used to connect application code to infrastructure.

Scope: this template applies selected DDD building blocks, including domain-owned modules, domain records, value objects, and domain validation. It does not claim that every module is a fully modeled bounded context with aggregates and a formally documented ubiquitous language.
Principle / pattern How it appears here Why use it
Modular monolith Business domains live in services/identity/app/modules/<domain>; one application is deployed. Preserves clear ownership and testable boundaries without premature network and operational complexity.
Layered / inward dependencies Router → application use case → domain/ports; infrastructure implements ports, and the composition root wires adapters. Business rules stay independent from HTTP, SQLAlchemy, and vendor clients.
Dependency injection Per-domain containers are composed in app/container.py; routes use provider paths. Dependencies are visible, replaceable, and controllable in tests.
DDD: domain modeling Domain-owned modules group related business capabilities. Domain records and value objects live separately from transport schemas and ORM models; for example, TodoRecord is mapped from the ORM row by the repository adapter, and scripts/new_module.py scaffolds a name value object and a uniqueness policy. Keeps business vocabulary and validation rules close to the capability they govern, rather than coupling them to HTTP or persistence.
SOLID: Single Responsibility Principle Routers handle HTTP translation, application services coordinate workflows, domain types represent business concepts, and repositories handle persistence. Gives each component a focused reason to change and makes responsibilities easier to test independently.
SOLID: Open/Closed Principle Use cases depend on ports, such as TodoRepositoryPort, so an adapter can be replaced or extended without rewriting the application workflow. Supports new infrastructure implementations while keeping application behavior stable.
SOLID: Liskov Substitution Principle Concrete adapters and test fakes must preserve the behavior and type expectations of the protocol they implement. Lets callers use alternate implementations without changing their expected outcomes.
SOLID: Interface Segregation Principle Application ports describe collaborator capabilities, such as repository operations or email sending, rather than exposing concrete infrastructure objects. Avoids forcing consumers to depend on unrelated infrastructure methods.
SOLID: Dependency Inversion Principle High-level application services depend on protocols; low-level adapters implement those protocols and are wired by the composition root. Business workflows stay independent of SQLAlchemy and vendor-specific implementations.
Separation of concerns and inward dependencies The request path separates HTTP routing, application workflows, domain concepts, and infrastructure persistence. Cross-module workflows use public application/service APIs rather than private repositories. Limits change propagation and makes module responsibilities and dependencies easier to understand.
Ports and adapters Application ports define required persistence or integration behavior; repository and integration adapters implement those contracts and are connected in the composition root. Makes application workflows testable without requiring production infrastructure and isolates implementation details.
Repository and mapping pattern Persistence repositories implement application contracts and map between SQLAlchemy models and persistence-independent records. Keeps database queries and ORM mapping out of use cases.
Cross-cutting concerns Middleware, shared dependencies, and exception handlers centralize request IDs, logging context, request limits, authentication, authorization, CSRF checks, rate limits, transaction scope, and RFC 9457 error translation. Applies consistent policies across endpoints without duplicating infrastructure logic in every feature.
Transaction-first integrity Writes are executed inside a request-scoped unit of work, with success committed once and errors rolled back. Prevents partial updates, reduces race-related bugs, and keeps database state consistent with business intent.
Explicit contracts FastAPI schemas, Pydantic validation, and typed client models define payloads and responses before logic runs. Encourages predictable APIs, earlier validation, and safer cross-team integration.
Idempotent writes POST and PATCH endpoints can use Idempotency-Key handling and replay-safe response storage. Makes retries safe for clients and reduces duplicate side effects during network interruptions and browser reloads.
Secure by default JWT-based auth, password hashing, CSRF protection, ownership checks, rate limiting, and request validation are part of the platform baseline. Security is treated as a default requirement rather than a late-stage add-on.
Async effects and outbox flow Business events are persisted with the transaction and dispatched after commit by ARQ workers. Keeps local data integrity while allowing reliable external follow-up work without breaking transactional guarantees.
Observability and recovery Structured logs, OpenTelemetry tracing, Sentry reporting, and health-focused middleware help understand runtime behavior. Makes operators and developers able to diagnose failures quickly and maintain production confidence.
Frontend/backend alignment Zod schemas, React Query flows, and versioned API contracts keep the UI and backend synchronized. Reduces mismatches between client assumptions and server reality and speeds up feature delivery.

Request transactions, error translation, retry safety, migrations and API contracts are explained in the request workflow and the relevant engineering-area sections below.

Architecture at a glance

The composition root wires infrastructure adapters to application ports and use cases. Module boundaries are checked by tests; a module can call another module's public application API, not its private repository or router.

Database sessions, error mapping, logging, security middleware, and API registration are application-level infrastructure. The browser never talks directly to repositories.

End-to-end request workflow

This follows an authenticated create/update request from the client to PostgreSQL and back. A client may send an Idempotency-Key on POST or PATCH to make retries safe.

On narrow screens, scroll the diagram horizontally. It is keyboard focusable for users who navigate without a pointer.

  1. 1 Client request Method, URL, body, cookies and headers.
  2. 2 Idempotency gate Optional claim, replay or retry conflict.
  3. 3 Core middleware Request ID, size limit, transaction scope.
  4. 4 CSRF middleware Reject unsafe cookie requests without a valid token.
  5. 5 Route and validation Match endpoint, rate-limit and validate input.
  6. 6 Authentication and access Resolve user, permissions and ownership.
  7. 7 Application use case Coordinate the requested business operation.
  1. 8 Domain rules Entities, value objects and policies.
  2. 9 Application port Describe the persistence need without SQL details.
  3. 10 Infrastructure adapter Map records and execute async persistence operations.
  4. 11 PostgreSQL Read/write within the request transaction.
  5. 12 HTTP result mapping Serialize response or RFC 9457 error.
  6. 13 Transaction decision Commit success; roll back error responses.
  7. 14 Response completion Return request ID and store an eligible replay result.

What each stage does

Stage Component Responsibility and why it exists
1 Client Sends the requested operation and user input. Cookies, CSRF headers, idempotency keys and conditional headers provide session security, safe retries and concurrency protection where applicable.
2 Idempotency middleware For keyed POST/PATCH requests, claims a key in a separate short transaction. It replays a completed result, rejects key/body mismatches, and prevents concurrent duplicate execution; without a key the request passes through.
3 Core middleware Binds a trusted request ID and logging context, enforces the declared body-size limit, measures the request, and opens the one database scope used by the endpoint.
4 CSRF middleware Checks unsafe requests authenticated by cookies before the route executes. This blocks cross-site state changes that could otherwise ride on a browser's automatically sent session cookie.
5 Router and request validation Selects the versioned endpoint, applies rate limits, and validates path/query/body data against Pydantic schemas. Invalid transport input is rejected before application logic runs.
6 Authentication and authorization dependencies Resolve the current user, check permissions and resource ownership. Centralizing these checks gives routes a consistent access-control policy before invoking a use case.
7 Application use case/service Coordinates the business operation, obtains needed facts, calls domain behavior, and uses ports or other modules' public application APIs. It should not know HTTP schemas, SQLAlchemy models or concrete adapters.
8 Domain model and policy Entities protect state transitions; value objects validate meaningful values; policies express business decisions. These rules remain executable without a database or web request so they are easy to review and test.
9 Application port Defines the capability the use case needs as a Python protocol. The dependency points inward, so persistence can be replaced without changing business logic.
10 Infrastructure adapter Implements the port, translates between domain/application records and ORM rows, and owns SQLAlchemy query details. It flushes when required but never commits.
11 PostgreSQL Executes reads and writes under the shared request transaction. Constraints provide final protection against races such as duplicate values that a prior policy check cannot prevent alone.
12 Response serialization and error handlers The route maps successful application results to response schemas and headers. Central handlers turn validation, domain/application and unexpected failures into RFC 9457 Problem Details without exposing internal exceptions.
13 Unit of work boundary The core middleware commits once when the final response is successful and rolls back error responses, discarding success-only callbacks. Explicit persistence on selected security failures is a narrow exception.
14 Response completion Adds X-Request-ID for client/log correlation. The idempotency layer stores responses below 500 and releases 5xx results. The response wrapper preserves after-commit work, which runs after the body is sent.

1 · Architecture and code organization

Layered migration complete

Backend modules under services/identity/app/modules/ separate domain records and rules, application use cases and ports, HTTP schemas/routes, and infrastructure persistence adapters. Existing module application workflows use repository ports and map between SQLAlchemy models and domain/application records in their infrastructure adapters. Architecture tests enforce inward dependencies and keep HTTP and persistence concerns out of application/domain code. The app is a modular monolith: modules communicate through public application APIs and run and deploy together.

This favors code ownership, local calls, and simple transactions while the domain is still changing. Extract a service only when an independent scaling, release, reliability, or team-ownership need justifies the distributed-systems costs.

Developer rule

Domain code must not import FastAPI, Pydantic, SQLAlchemy, shared infrastructure, or other modules. Application workflows depend on contracts in application/ports/, never concrete adapters. Routes own HTTP validation/serialization; adapters map domain/application records to ORM models. Cross-module calls use another module's public application API. Let the composition root wire providers. Document material architectural changes as ADRs.

2 · API design and contracts

Strong baseline

The API uses URL major versions (/v1, /v2), RFC 9457 Problem Details with stable error codes, Pydantic validation, camelCase JSON aliases, capped offset pagination, cursor pagination for suitable feeds, allow-listed filters/sorting, idempotency keys, and ETags/If-Match on versioned resources.

OpenAPI is checked in CI, generated TypeScript types are checked for drift, and API breaking changes are compared against the target branch. Request bodies are capped in middleware and ingress configuration.

When adding an endpoint

  • Use resource-oriented paths and define the success/error contract and stable codes.
  • Apply the repository's page-size limit; use a cursor for large append-heavy lists.
  • Require idempotency keys on operations where clients may retry side effects.
  • Regenerate services/identity/openapi.json and web/src/lib/api-types.gen.ts.
  • Update docs/API_FLOW.md and include authorization/negative tests.

3 · Data layer

Strong baseline

SQLAlchemy 2 async models inherit audit, soft-delete, and optimistic-version columns from BaseModel. Alembic migrations, PostgreSQL constraints, query filters, connection pooling, slow-query logging, statement timeouts, and a distinct migration/runtime-role pattern are represented.

Use one transaction per request/use case. Do not commit from a service or repository. Review generated migrations, add indexes for real query patterns, use the expand/contract approach, and update docs/DATABASE_DESIGN.md after schema changes.

Product decisions still needed

  • Choose row-, schema-, or database-level tenant isolation where applicable.
  • Measure connection demand before raising HPA, worker concurrency, or pool limits.
  • Design read replicas and retention around consistency, latency, and legal needs.
  • Prove backup restoration and point-in-time recovery against your RPO/RTO.

4 · Security

Useful controls; security review remains application-specific

The starter includes short-lived access cookies, rotating opaque refresh tokens, revocation, optional MFA, verification/reset tokens, password hashing, CSRF checks, role permissions, centralized ownership checks, rate limits, request-size limits, trusted-host/CORS configuration, safe secret validation, redacted logs, audit events, dependency scanning, Bandit, secret scanning, container scanning, and image signing.

Prometheus scraping can use a bearer secret via METRICS_TOKEN; the metrics endpoint must remain private or require a configured token. The test suite checks missing, incorrect, and correct credentials. This endpoint is not a substitute for network restrictions.

An application must decide whether to delegate authentication to OIDC, add tenant-aware authorization, harden account recovery, and run feature-specific threat modelling and penetration tests. Do not infer GDPR/HIPAA compliance from these controls.

5 · Reliability and resilience

Strong baseline

Liveness is separate from dependency-aware readiness. Shutdown drains requests before pooled clients close. Outbound HTTP has configured timeouts, retry/backoff, and circuit breaker behavior. ARQ runs scheduled/queued work; the PostgreSQL transactional outbox retries at-least-once delivery and dead-letters exhausted events.

SLO targets, burn-rate alerts, runbooks, and disaster-recovery procedures are documented. Teams must choose service-specific SLOs, verify that alert owners can respond, and run recovery drills rather than treating written RPO/RTO values as evidence.

6 · Observability

Implemented foundation

Structured JSON logs include request and trace context, with common secret/PII redaction. Prometheus exposes request rate, errors, duration, pool saturation, and outbox backlog metrics. OpenTelemetry instruments FastAPI, SQLAlchemy, and HTTP clients with sampling. Sentry is release-tagged and scrubs request credentials/data. Dashboard, alerts, and operational runbooks are checked in.

Configure an OTLP collector, Sentry DSN, metrics authentication/network policy, log access, retention, and alert destinations per environment. Avoid high-cardinality labels such as user IDs.

7 · Performance and scalability

Scalable mechanisms; benchmark your workload

API/worker processes are stateless, DB pools are configurable, queries have pagination limits, uploads use private object storage in production examples, and Helm provides resource requests/limits, topology spread, and autoscaling. CPU-intensive password hashing is sent off the event loop. A scheduled staging k6 smoke test checks latency and error thresholds.

A smoke load test is not a capacity study. Establish production traffic shape, payload sizes, queue lag tolerance, database connection budget, cache invalidation rules, and autoscaling behavior with representative data before selecting instance sizes.

8 · Testing strategy

Broad baseline; extend with domain cases

Pytest covers unit, integration, and architecture behavior. Integration tests use PostgreSQL via Testcontainers and roll back test transactions. Backend coverage has a 90% gate; security-sensitive code has scheduled mutation testing. Vitest/RTL cover frontend behavior; Playwright E2E exercises browser flows. CI now runs Chromium E2E against a disposable Compose API stack and checks Helm/Terraform.

Backend tests refuse a TEST_DB_HOST override because suite setup recreates the schema; Docker must be available. Keep E2E pointed only at a disposable local/CI environment. Add cross-tenant/ownership denial, concurrency, failure, and authorization tests for every new feature.

9 · CI/CD and release management

Pipeline included; repository governance is external configuration

Pull requests run backend/frontend lint, types, tests, OpenAPI drift checks, migration round-trip, dependency and static analysis, secret scanning, image scans, frontend budgets, browser E2E, and Helm/Terraform validation. Release builds images once, adds SBOM/provenance, signs images, deploys the same digests to staging and then protected production, and runs smoke checks.

Configure branch protection, CODEOWNERS enforcement, environment approvals, OIDC cloud trust, staging/production variables, and release permissions in GitHub. A workflow file cannot activate those repository-level policies by itself.

10 · Infrastructure and deployment

Secure deployment example; cloud platform prerequisites remain

Docker images use multi-stage builds and non-root users. Helm provides API, worker, web, migration jobs, probes, network policies, resource settings, and autoscaling. Terraform examples provision an AWS VPC, private managed Postgres/Redis, S3 storage, and secrets. CI validates chart rendering and Terraform configuration.

The EKS cluster, DNS, ingress controller, certificate automation, External Secrets Operator, and monitoring operators are assumed platform services. Terraform now requires a workload security group and an environment-specific remote-state backend. Release deployment rejects empty/example domain and bucket inputs.

Start with the deployment runbook. Review network access, KMS policies, DB roles, image repositories, bucket lifecycle, autoscaling, WAF, and rollbacks with your platform team.

11 · Configuration management

Typed settings and fail-closed production defaults

Pydantic Settings reads environment configuration, validates types and rejects insecure deployed secrets/defaults. Local configuration examples are separate from production Kubernetes Secrets, which are expected to come from a secrets manager. Add a feature-flag capability when the product needs controlled release of risky features.

Do not commit real .env files. Keep staging and production credentials distinct, rotate secrets with a tested rollout, and confirm every new setting has a safe default or a startup validation rule.

12 · Frontend

Production-oriented frontend foundation

React 19 and TypeScript are arranged by route and feature. TanStack Router handles route-based code splitting, TanStack Query manages server state, Zod validates client input, and Axios sends HttpOnly-cookie sessions with CSRF headers. Error boundaries, Sentry, accessibility checks, Lighthouse budgets, and unit/E2E tooling are configured.

Keep API types generated from OpenAPI. Product teams own page-level usability, accessibility acceptance, localization, consent, CDN policy, and any real-user metrics strategy.

13 · Developer experience

Strong starter workflow

Docker Compose provides a local full stack. Task commands cover backend and frontend development, checks, migration, API generation, and tests. scripts/new_module.py scaffolds a domain and registers it. Onboarding, coding standards, ADRs, pull-request templates, CODEOWNERS, pre-commit guidance, and editor tasks make the intended workflow discoverable.

Generated files are a starting point, not unquestionable code: review authorization, ordering/filter allow-lists, database indexes, status transitions, and error behavior for the new domain.

14 · Governance, compliance, and data privacy

Useful privacy controls; not a compliance certification

The repository includes data classification, retention guidance, an account deletion flow, field encryption for sensitive secrets such as MFA seeds, append-oriented audit records, least-privilege guidance, access-review practices, and dependency licence checks.

The organization must decide the lawful basis, consent, data residency, retention periods, subject-request process, incident reporting, access evidence, encryption keys, and processor agreements applicable to its customers. HIPAA, GDPR, CCPA, and similar obligations require a full organizational and deployment assessment.

Worked example · add a Project entity

The example creates a project owned by the authenticated user, with a name, standard audit/version fields, paginated listing, and ownership-checked read/update/delete operations. It demonstrates the template workflow; generated code must be reviewed and adapted to your domain.

The request lifecycle is shown once in End-to-end request workflow. The steps below focus on implementing the module; they do not repeat the runtime path.

1

Generate the domain scaffold

cd services/identity
uv run python scripts/new_module.py projects

The layered generator creates app/modules/projects/ with domain/, application/ports/, application/use_cases/, infrastructure/persistence/, HTTP schemas/routes, DI wiring, and focused unit-test skeletons. It also registers the ORM model, container, and versioned router. Review all generated changes before continuing.

2

Define domain value and entity

Domain classes are plain Python and must not import HTTP, SQLAlchemy, or infrastructure. The name value object owns the normalization and length invariant. The entity carries its identity and owner; it is not the SQLAlchemy row. 

@dataclass(frozen=True, slots=True)
class ProjectName:
    value: str

    def __post_init__(self) -> None:
        normalized = self.value.strip()
        if not normalized or len(normalized) > 200:
            raise ProjectNameInvalid("Name must contain 1–200 characters")
        object.__setattr__(self, "value", normalized)


@dataclass(frozen=True, slots=True)
class Project:
    id: UUID
    user_id: UUID
    name: ProjectName
3

Define request and response schemas

Keep the transport schema separate from both domain and persistence types. Pydantic validates the HTTP shape; the ProjectName value object still enforces the business invariant when the use case is called from another entry point. 

from datetime import datetime
from pydantic import BaseModel, ConfigDict, Field
from pydantic.alias_generators import to_camel
from uuid import UUID


class ProjectCreate(BaseModel):
    model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True)
    name: str = Field(min_length=1, max_length=200)
    description: str | None = Field(default=None, max_length=4000)


class ProjectUpdate(BaseModel):
    model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True)
    name: str | None = Field(default=None, min_length=1, max_length=200)
    description: str | None = Field(default=None, max_length=4000)


class Project(BaseModel):
    model_config = ConfigDict(
        alias_generator=to_camel,
        populate_by_name=True,
        from_attributes=True,
    )
    id: UUID
    name: str
    description: str | None
    created_at: datetime
    updated_at: datetime
4

Put domain decisions in policies

A policy is a pure decision with explicit facts. For example, the create-project use case asks its repository port whether this owner already has the normalized name, then applies the domain policy. Keep fetching facts out of the policy and keep HTTP status mapping out of the domain. 

def ensure_project_name_available(name: str, *, already_exists: bool) -> None:
    if already_exists:
        raise ProjectNameAlreadyExists(name)

# In CreateProject.execute:
name = ProjectName(requested_name)
exists = await repository.exists_by_name(user_id, name.value)
ensure_project_name_available(name.value, already_exists=exists)
return await repository.add(Project.create(user_id=user_id, name=name))

A database uniqueness constraint is still required to close the race between the check and insert. Translate the resulting conflict to a stable application error.

5

Use ports to orchestrate external checks

Define a protocol in application/ports/eligibility.py for any remote decision, inject it into CreateProject, and provide its adapter in the module container. The use case decides what to do with the result; the adapter owns HTTP, timeouts, and provider-specific response parsing. 

class ProjectEligibility(Protocol):
    async def may_create(self, owner_id: UUID) -> bool: ...

# In the use case, before persistence:
if not await eligibility.may_create(user_id):
    raise ProjectCreationNotAllowed()

Set explicit timeouts and define retry/failure behavior. Do not keep a database transaction open while waiting on a slow provider; use the outbox for post-commit side effects.

6

Implement and wire the persistence adapter

Keep the SQLAlchemy Projects model in infrastructure/persistence/models.py. Implement the application repository port in infrastructure/persistence/repository.py, map ORM rows to domain entities on reads, and map entities to rows on writes. Never return ORM models from the application boundary. 

repository = providers.Factory(
    SqlAlchemyProjectRepository,
    session=db.provided.scoped_session,
)
create_project = providers.Factory(
    CreateProject,
    repository=repository,
    eligibility=eligibility_checker,
)
7

Expose a versioned, ownership-protected API

The scaffold provides the create route. Add list/get/patch/delete routes only when required, following the same rule: validate at the HTTP boundary, call an application use case, and use the centralized ownership dependency for resource access. Apply rate limits and scope list queries to the current user. 

POST   /v2/projects/       scaffolded: create a project (201)
GET    /v2/projects/       list the current user's projects
GET    /v2/projects/{id}   get an owned project
PATCH  /v2/projects/{id}   update an owned project
DELETE /v2/projects/{id}   soft-delete an owned project (204)

Example request:

{
  "name": "Website refresh",
  "description": "Plan the public site redesign."
}

The API accepts the same field names in snake_case; output aliases are camelCase. For a new domain, verify the generated endpoint paths and response shapes in OpenAPI rather than assuming the example is the final contract.

8

Create and review the migration

cd services/identity
uv run alembic revision --autogenerate -m "create projects"
# Review the generated upgrade() and downgrade() before applying.
uv run task upgrade

Verify foreign keys, indexes, uniqueness, nullability, server defaults, and lock/rewriting impact. For a non-null field on a large existing table, use expand/backfill/contract rather than a single disruptive migration. Update docs/DATABASE_DESIGN.md.

9

Test behavior and regenerate contracts

  • Unit-test value objects and policies; test use cases with fake ports and adapter mappings separately.
  • Integration-test create/list/get/update/delete and invalid input.
  • Prove another user's project returns not-found/forbidden per policy.
  • Test pagination caps, idempotent replay, and stale ETag conflict behavior.
  • Update docs/API_FLOW.md and database documentation. 
cd services/identity
uv run task test
uv run task openapi

cd ../../web
pnpm gen:api
pnpm build
pnpm test

Run backend tests with Docker available: pytest uses a throwaway Postgres Testcontainers instance and refuses an externally configured TEST_DB_HOST.

Frontend follow-through: add a Project Zod model, query/mutation hooks, feature components and authenticated routes only if this product needs a UI. Keep API request/response types generated from OpenAPI; keep page-specific behavior in web/src/features/.

Production adoption checklist

Before the first feature

  • Decide domain boundaries, ownership, tenant isolation, and identity-provider needs.
  • Replace project name, email provider, allowed origins, error-doc URLs, and branding.
  • Choose data classifications, retention, audit scope, and deletion guarantees.
  • Define the first API compatibility and migration policy with the team.

Before staging

  • Provision Terraform state bucket/lock table and platform prerequisites.
  • Set workload security groups, domains, image repositories, and upload buckets.
  • Provision Secrets Manager values and a least-privilege DB app/migration role.
  • Configure OIDC, DNS/TLS, ingress/WAF, OTLP, Sentry, and Prometheus access.

Before production

  • Enforce protected branches, required reviews, CODEOWNERS, and production approvals.
  • Run threat modelling, security testing, and workload-representative load tests.
  • Prove migrations, rollback behavior, graceful drain, and incident runbooks.
  • Restore a backup and measure actual RPO/RTO; retain drill evidence.

Continuously

  • Review error budgets, alert quality, slow queries, pool saturation, and queue lag.
  • Patch dependencies and base images; rotate secrets and review access.
  • Revisit SLOs, capacity, retention, privacy obligations, and recovery readiness.
  • Promote the same signed image digest; do not rebuild for production.
