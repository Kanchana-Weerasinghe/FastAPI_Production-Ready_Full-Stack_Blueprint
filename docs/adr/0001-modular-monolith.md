# 0001. Modular monolith with per-module DI containers

- Status: Accepted
- Date: 2026-10-16

## Context

The template must scale to large projects and teams. Grouping code by technical layer (`routes/`, `services/`, `repositories/`) spreads every feature across the whole tree, encourages hidden coupling between features, and makes it hard to later extract a feature into its own service. Starting with microservices adds network, deployment and consistency costs before the domain boundaries are known.

## Decision

- The backend is one deployable modular monolith organized by business domain under `app/modules/<name>/`.
- Modules use an explicit inward dependency direction:

  ```text
  router -> application use cases -> domain
                            |             ^
                            v             |
                    application ports <- infrastructure adapters
  ```

- `domain/` contains framework- and persistence-independent entities, value objects, policies, and domain exceptions. Keep rules with the entity/value object they constrain; use policies for decisions spanning multiple concepts.
- `application/use_cases/` coordinates workflows. It should depend on contracts in `application/ports/`, invoke domain behavior, and control transaction-aware operations; it must not import SQLAlchemy repositories or HTTP types.
- `infrastructure/persistence/` owns SQLAlchemy models, repository implementations, and mappings. Other adapters (HTTP clients, object storage) live under `infrastructure/integrations/`.
- `router.py` and `schemas.py` are the HTTP boundary. Routes validate/translate transport input and call application use cases; schemas are not domain entities.
- The root composition container wires each module's application ports to infrastructure adapters. Cross-module calls use a module's application-facing public API, never its ORM models or repositories.
- Existing modules have been moved into `application/` and `infrastructure/persistence/`. Root `service.py`, `repository.py`, and `models.py` files remain as **temporary compatibility re-exports** for tests and older internal callers. This is a structural migration, not yet a complete domain/persistence separation: several existing application services still depend on ORM models and concrete repositories. New modules generated by `services/identity/scripts/new_module.py` use pure domain entities and repository ports; migrate existing workflows toward that pattern incrementally, without calling the transition complete until the ORM dependencies are removed.
- `core` remains framework/infrastructure policy, `shared` contains reusable technical building blocks, feature modules own product behavior, and `app/container.py`, `app/api.py`, and `app/main.py` are composition/entry points.
- Architecture tests enforce module public APIs and keep domain code framework/persistence independent. They do not yet prohibit every legacy application-to-infrastructure dependency. `services/identity/scripts/new_module.py` scaffolds the target layered pattern.

## Consequences

- A module can be extracted into a service by replacing its in-process service calls with an API/queue client behind the same interface.
- There is more boilerplate per module (domain/application/ports/adapters and mapping), offset by the scaffold and clearer rule ownership.
- Cross-module database relationships (e.g. a `projects.user_id → users.id` foreign key) remain; extracting a module later requires replacing those foreign keys with IDs owned by the other service.
- Compatibility re-exports reduce migration risk but are transitional and should be removed once callers and tests use the layered API.
